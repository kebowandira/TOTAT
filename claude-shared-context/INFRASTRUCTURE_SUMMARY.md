## Cross-server SSH access via agent forwarding (set up 2026-09-23)

Owner asked to be able to manage all VPS from one place (NL1) without concentrating private keys there (which would make NL1 a much bigger target if ever compromised). Implemented via **SSH agent forwarding**, not key copying:
- `~/.ssh/config` on NL1 now has short aliases: `dasabo` (43.240.149.38:2298), `mail1` (43.240.149.83:27194), `nl1` (62.105.222.90:2299) — hostnames/ports only, **no private keys involved, safe to leave in place permanently**.
- To use it: load the relevant private keys into a local ssh-agent (`eval $(ssh-agent -s)`, then `ssh-add` each key — id1_v3 for Dasabo, nl1_new for NL1, mail1_ed25519 for MAIL1), then connect with `ssh -A -p 2299 -i ~/.ssh/nl1_new bule@62.105.222.90`. From inside that session, `ssh dasabo` / `ssh mail1` work directly using the forwarded agent — the keys themselves never touch NL1's disk.
- **Important for future sessions/scripts:** `eval $(ssh-agent -s)` sets environment variables (`SSH_AUTH_SOCK`) that only persist within the SAME shell/process — if your tool invokes each command as a fresh subprocess (no persistent shell state), you must start the agent, add keys, AND run the forwarded SSH command all within one single invocation, or the forwarding silently fails with "Permission denied."
- MassiveGrid was NOT included in this setup — no local key found under an obvious name (`mg_*`/`massivegrid_*` in `~/.ssh/`); its access hasn't been re-verified since July 2026 per the existing open item below. Add it once that key is located/confirmed.

## Parameter auto-tuning + wrapper-down alerting + real outage (2026-09-30)

Owner agreed to the phased "self-improving EA" plan from the prior session (parameter auto-tuning first, not logic-rewriting) and separately hit a real ~4-hour Windows VPS outage mid-session.

**Parameter auto-tuning, built and verified live end-to-end:**
- `strategy/filters.py`: all SL/TP ATR multipliers centralized into `DEFAULT_PARAMS` (per engine/variant) + a new `get_params()` that merges in an optional `tuning_overrides.json` (git-ignored, lives next to filters.py on the Windows box), re-read from disk on every call so an approved change takes effect on the very next signal check, no restart needed - same live-reload pattern `executor.py` already uses for `.env`. A tuned value is clamped to `TUNING_BOUNDS` (60-180% of the original default) inside `get_params()` itself, independent of whatever bounds proposed it.
- `mt5/tuning.py` (new): grid-searches SL/TP multipliers (5x5 grid, ±30/15% steps) around each real detector's *existing* fires - one detection pass, then cheap SL/TP resolution per candidate, same walk-forward method as `backtest_engines.py` (no lookahead into the signal). Only proposes a change if expectancy improves by ≥0.05R over the current default AND has ≥30 resolved samples: otherwise reports `insufficient_data` or `no_improvement`, never a forced answer.
- `wrapper_api.py`: new `GET /tuning/proposals` (runs the grid search live, ~1-2 min at bars=5000 across all 7 real-detection variants - lowered from 8000 after real timing showed that was too slow), `POST /tuning/apply` (re-validates bounds server-side against `DEFAULT_PARAMS`/`TUNING_BOUNDS` regardless of caller input), `POST /tuning/revert`.
- Dashboard: new **Tuning** page (`/tuning`) - a "Refresh tuning candidates" button pulls proposals into a new `tuning_proposals` table, each with current vs proposed multipliers and the actual backtest stats (win rate/n/expectancy) behind the recommendation; Approve calls `/tuning/apply` and marks the row `applied`; Reject just marks it `rejected`. **No scheduled/automatic application** - explicit owner decision: the EA tunes its own dials, but only with a human approving each specific change, same trust model as trade execution itself.
- Verified for real: refreshed against live data, got 5 genuine proposals (e.g. SBB-B1-extreme: 1.5/2.25 → 1.05/2.925 ATR, baseline 40.5% WR/n=168/exp=+0.012R → proposed 31.5% WR but exp=+0.194R - a real "wider target compensates for lower hit rate" tradeoff, not noise, since n held at 168 both ways), approved one, confirmed `tuning_overrides.json` was written on the Windows box with the exact clamped values, then reverted it via `/tuning/revert` - full loop confirmed working before leaving any real change applied.
- Cross-referenced `kebowandira/APEX`'s own independent SBB/HABE-trend-v1 experiment (2025 BTCUSDT, different market, not directly transferable) in `filters.py`'s docstring: their numbers point the same direction as our own real backtest - the trend-alignment filter isn't a demonstrated improvement on either dataset.

**Wrapper down/recovery Telegram alerting (built same session, motivated by the outage below):** `collector.py`'s `collect_mt5()` now tracks consecutive failures in a new `wrapper_health` row and alerts after 2 consecutive failed 15-min cycles (~30 min), with a recovery message once it's back, capped to at most one re-alert per 2 hours while still down.
