## Cross-server SSH access via agent forwarding (set up 2026-09-23)

Owner asked to be able to manage all VPS from one place (NL1) without concentrating private keys there (which would make NL1 a much bigger target if ever compromised). Implemented via **SSH agent forwarding**, not key copying:
- `~/.ssh/config` on NL1 now has short aliases: `dasabo` (43.240.149.38:2298), `mail1` (43.240.149.83:27194), `nl1` (62.105.222.90:2299) — hostnames/ports only, **no private keys involved, safe to leave in place permanently**.
- To use it: load the relevant private keys into a local ssh-agent (`eval $(ssh-agent -s)`, then `ssh-add` each key — id1_v3 for Dasabo, nl1_new for NL1, mail1_ed25519 for MAIL1), then connect with `ssh -A -p 2299 -i ~/.ssh/nl1_new bule@62.105.222.90`. From inside that session, `ssh dasabo` / `ssh mail1` work directly using the forwarded agent — the keys themselves never touch NL1's disk.
- **Important for future sessions/scripts:** `eval $(ssh-agent -s)` sets environment variables (`SSH_AUTH_SOCK`) that only persist within the SAME shell/process — if your tool invokes each command as a fresh subprocess (no persistent shell state), you must start the agent, add keys, AND run the forwarded SSH command all within one single invocation, or the forwarding silently fails with "Permission denied."
- MassiveGrid was NOT included in this setup — no local key found under an obvious name (`mg_*`/`massivegrid_*` in `~/.ssh/`); its access hasn't been re-verified since July 2026 per the existing open item below. Add it once that key is located/confirmed.

## MAIL1 Docker outage found and fixed (2026-09-25)

While preparing the final catch-up sync, MAIL1 was discovered to have **zero mail service running** — no listening ports on 25/80/443/587/465/993/995/143/110/4190 at all. Root cause chain, fully diagnosed and fixed:
- MAIL1 rebooted around 2026-09-25 02:03 UTC (likely during the owner's VNC-console password-recovery attempts earlier that session — see credentials section above). On boot, **`dockerd` itself crash-looped and gave up** (`systemctl` showed `docker.service` failed, "Start request repeated too quickly") — its own Go runtime hit a fatal `out of memory allocating heap arena map` error, confirmed via `journalctl -u docker`.
- Real cause: MAIL1 had **`vm.overcommit_memory=2` (strict) with zero swap**, leaving `Committed_AS` within ~67MB of `CommitLimit` — any new process reserving a large virtual address space (which Go binaries like `dockerd`/`docker`/`docker-proxy` do upfront regardless of actual usage) could get its memory reservation rejected outright, independent of real free RAM (`free -h` showed 700MB+ "available" the whole time — irrelevant under strict overcommit accounting). This also explains earlier-session flakiness where some `docker exec` calls on MAIL1 crashed with the identical Go OOM signature.
- **Fixed in two parts:** (1) added a 1GB swapfile (same pattern as the other boxes — MAIL1 never had one), which raised `CommitLimit` but still left the daemon failing on `docker-proxy` spawns (per-port helper processes, same Go-OOM signature, blank error text) once several containers were already running and headroom got tight again. (2) **Set `vm.overcommit_memory=0`** (the standard Linux heuristic default, persisted in `/etc/sysctl.conf`) — this is what essentially all Docker hosts run under, and is the real fix; strict overcommit mode is a poor fit for a small single-purpose box running many small Go-based container-runtime helper processes.
- **Bonus find while restarting:** MAIL1's own `/mailu/docker-compose.yml` and `mailu.env` had **the exact same hardcoded-old-IP bug** found and fixed on OrangeVPS's restored copy (10 port-binding lines + `BIND_ADDRESS4` pinned to `45.146.202.198`, MAIL1's pre-September IP) — except this is the *original source* of that bug, dormant on MAIL1 itself since its own IP change because the already-running containers never needed to rebind. Fixed the same way (sed-replaced to `43.240.149.83`). **Lesson: this bug pattern should be checked on any Mailu box after an IP change, not just during migrations.**
- All 7 containers (front/admin/imap/smtp/antispam/redis/webmail) confirmed healthy and correctly bound to `43.240.149.83` after the fix. MAIL1 is now actually functional as the cutover's rollback option — it was NOT during the ~24h it sat crashed, which the owner should know given it was being relied on as a safety net.
- **Checked `vm.overcommit_memory` on all other boxes (NL1, OrangeVPS, RackNerd, GreenCloud) — all already `0` (default), MAIL1 was the only outlier.** No fleet-wide issue, just this one box.
- **Two of the fix commands (`systemctl start docker`, `docker-compose up -d`) were blocked by this session's sandbox classifier** (flagged as risky remote writes) and had to be run by the owner directly in their own terminal rather than by the assistant — a recurring pattern worth expecting for service-start/container-start commands specifically (read-only checks and file edits via `sed` were not blocked).
